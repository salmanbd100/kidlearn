# 03 — Auth & Profile Database Schema

> **Estimated effort:** 3–4 hours
> **Depends on:** 02
> **Requirement IDs:** FR-AUTH-03, FR-PROF-01, FR-PROF-02, FR-PROF-07, NFR-SAFE-03, spec §8

## Goal
Add the first real domain models to `packages/db`: `Parent` (Google identity, email, nullable PIN hash, COPPA consent record), `AdminUser` (internal CMS role), and `ChildProfile` (name, age, grade level, preferred language, avatar placeholder) with a cascading Parent → ChildProfile relation. Ship the **initial Prisma migration** for the project and a seed script stub, so files 04–06 can keep layering models and the auth/profile APIs (files 09–11) have their tables ready.

## Context & Current State
- Files 01–02 are done: Vitest runs everywhere; `packages/db` has a working Supabase connection (pooled `DATABASE_URL` + `DIRECT_URL`), a generator/datasource-only `schema.prisma`, the exported `prisma` singleton, and a passing `GET /health/db`. **No migrations exist yet** — `prisma migrate dev` here creates `prisma/migrations/` and the `_prisma_migrations` table.
- The earlier starter `Parent`/`Child` demo models were removed in file 02; nothing in `apps/server` references domain models.
- Auth implementation (Google OAuth via better-auth, sessions, PIN verification endpoints) comes later (files 09–10); this file only provides the **storage** they need. better-auth's own tables (session/account/verification) are generated by its CLI in file 09 — do not anticipate them here.

## Detailed Requirements
1. **Parent** stores the Google identity (`googleId` unique + `email` unique, plus display `name` and `avatarUrl` from the Google profile), per spec §4.2 / §8 ("auth identity, email, PIN hash, consent record").
2. **Parent.pinHash** is nullable `String` — the PIN gate (FR-AUTH-04, implemented in file 10) is set after first login, so a fresh account has no PIN yet. Only a hash is ever stored.
3. **Consent record (FR-AUTH-03, NFR-SAFE-03):** `consentGivenAt DateTime?` + `consentVersion String?` on Parent. Both null until the parent explicitly accepts; the API layer (file 11) must refuse child-profile creation while `consentGivenAt` is null. Storing the timestamp + accepted-text version satisfies COPPA/GDPR consent-record keeping (NFR-SAFE-06).
4. **AdminUser** is a separate model (id, unique email, name, `role` defaulting to `"admin"`) — admins are internal and never mix with parent accounts (spec §4.3, §8). **Credentials are NOT stored here:** admin sign-in uses better-auth's email/password provider (enabled in file 31), so the password hash lives on the better-auth `User` row. File 31 adds `authUserId String? @unique` to link `AdminUser` → `User`. Do **not** add a `passwordHash` column here — it would be an orphaned, never-populated field (see the alignment note in `database-design.md` §8).
5. **ChildProfile** captures exactly the FR-PROF-02 fields: `firstName`, `age Int`, `gradeLevel` enum (`NURSERY` | `KG1` | `KG2`), `preferredLanguage` enum (`en` | `bn`, default `en`), and `avatarCharacterRef String?` — a placeholder asset/slug reference until the `Character` model lands in file 06.
6. **Ownership & cascade:** `ChildProfile.parentId` is a required FK to Parent with `onDelete: Cascade`, so deleting a parent removes all child profiles (supports FR-AUTH-05 / NFR-SAFE-05 deletion; FR-PROF-07 owner-only access is enforced at the API layer by always filtering on `parentId`).
7. **≤5 profiles per parent (FR-PROF-01)** is enforced at the API layer (file 11). Optionally add a DB-level guard in the migration SQL (a trigger — Postgres CHECK constraints cannot count rows across a table); document the option, ship the API-level rule as authoritative.
8. The schema migrates cleanly (`pnpm db:migrate`) and a `prisma/seed.ts` stub runs via `prisma db seed`, creating one dev parent + one child profile idempotently (`upsert`).

## Technical Approach & Suggestions

**Files to modify:** `packages/db/prisma/schema.prisma`, `packages/db/package.json` (seed config + `tsx` devDep).
**Files to create:** `packages/db/prisma/seed.ts`, migration folder via CLI (`prisma/migrations/<ts>_auth_profile_schema/`).

Append to `schema.prisma` (exact models):

```prisma
enum GradeLevel {
  NURSERY
  KG1
  KG2
}

enum Language {
  en
  bn
}

model Parent {
  id             String    @id @default(uuid())
  googleId       String    @unique
  email          String    @unique
  name           String?
  avatarUrl      String?
  pinHash        String?   // set in file 10; bcrypt/argon2 hash, never the raw PIN
  consentGivenAt DateTime? // FR-AUTH-03 / NFR-SAFE-03: null until consent accepted
  consentVersion String?   // version of the consent text that was accepted
  createdAt      DateTime  @default(now())
  updatedAt      DateTime  @updatedAt
  children       ChildProfile[]
}

model AdminUser {
  id           String   @id @default(uuid())
  email        String   @unique
  name         String
  role         String   @default("admin")
  // No passwordHash: admin credentials live on the better-auth `User` row.
  // File 31 adds `authUserId String? @unique` (+ relation to User) to link them.
  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt
}

model ChildProfile {
  id                 String     @id @default(uuid())
  firstName          String
  age                Int        // 3–6; validated by Zod at the API layer (file 11)
  gradeLevel         GradeLevel
  preferredLanguage  Language   @default(en)
  avatarCharacterRef String?    // placeholder; becomes a Character FK in file 06
  parentId           String
  parent             Parent     @relation(fields: [parentId], references: [id], onDelete: Cascade)
  createdAt          DateTime   @default(now())
  updatedAt          DateTime   @updatedAt

  @@index([parentId])
}
```

Locale enum values are lowercase `en`/`bn` on purpose — they match i18next locale codes end-to-end (Shared Technical Decisions), so no mapping layer is needed.

**Optional DB-level ≤5 guard** (document in the migration as a comment; only enable if the team wants belt-and-braces):

```sql
CREATE OR REPLACE FUNCTION enforce_max_children() RETURNS trigger AS $$
BEGIN
  IF (SELECT COUNT(*) FROM "ChildProfile" WHERE "parentId" = NEW."parentId") >= 5 THEN
    RAISE EXCEPTION 'parent % already has 5 child profiles', NEW."parentId";
  END IF;
  RETURN NEW;
END; $$ LANGUAGE plpgsql;
CREATE TRIGGER max_children BEFORE INSERT ON "ChildProfile"
  FOR EACH ROW EXECUTE FUNCTION enforce_max_children();
```

If adopted, append it to the generated migration's `migration.sql` (Prisma preserves hand-edits) — but the API check in file 11 remains the user-facing enforcement (it returns a friendly error; the trigger only hard-stops bugs).

**Seed stub** — `packages/db/prisma/seed.ts`:

```ts
import { PrismaClient } from "@prisma/client";

const prisma = new PrismaClient();

async function main() {
  const parent = await prisma.parent.upsert({
    where: { email: "dev-parent@kidlearn.local" },
    update: {},
    create: {
      googleId: "dev-google-id",
      email: "dev-parent@kidlearn.local",
      name: "Dev Parent",
      consentGivenAt: new Date(),
      consentVersion: "dev-1",
    },
  });
  await prisma.childProfile.upsert({
    where: { id: "00000000-0000-0000-0000-000000000001" },
    update: {},
    create: {
      id: "00000000-0000-0000-0000-000000000001",
      firstName: "Ava",
      age: 4,
      gradeLevel: "NURSERY",
      preferredLanguage: "en",
      parentId: parent.id,
    },
  });
}

main().finally(() => prisma.$disconnect());
```

## Step-by-Step Plan
1. Add `GradeLevel` and `Language` enums plus the three models to `schema.prisma`; run `pnpm --filter @kidlearn/db exec prisma validate`. (~25 min)
2. Run `pnpm db:migrate` (name: `auth_profile_schema`); inspect the generated `migration.sql` — confirm `ON DELETE CASCADE` on the `ChildProfile.parentId` FK and the two unique indexes on Parent. (~20 min)
3. Decide on the optional ≤5 trigger with the team; if yes, append the SQL above to the migration file and re-run `pnpm db:migrate` on a reset DB (`prisma migrate reset`) to confirm it applies. (~20 min)
4. Run `pnpm db:generate && pnpm --filter @kidlearn/db build`; confirm `Parent`, `AdminUser`, `ChildProfile`, `GradeLevel`, `Language` types are exported from `@kidlearn/db`. (~15 min)
5. Add `tsx` devDep, the `prisma.seed` config, and `db:seed` script to `packages/db/package.json`; write `prisma/seed.ts`. (~25 min)
6. Run `pnpm --filter @kidlearn/db db:seed` **twice**; verify it succeeds both times (idempotent upserts) and rows exist in `prisma studio`. (~15 min)
7. Manually verify cascade: delete the seeded parent in `prisma studio`, confirm the child profile disappears; re-run `db:seed` to restore. (~15 min)
8. Full sweep: `pnpm lint && pnpm typecheck && pnpm test && pnpm build`. (~15 min)

## Schema additions in later files (forward references)

These models grow as later files land. The full final shape is consolidated in **`document/database-design.md`**. Tracked here so this doc stays aligned:

**Canonical consent field names (do not rename):** `Parent.consentGivenAt DateTime?` and `Parent.consentVersion String?`. Earlier API drafts referred to `consentAt` — that is the same column; files 09–10 use `consentGivenAt`.
